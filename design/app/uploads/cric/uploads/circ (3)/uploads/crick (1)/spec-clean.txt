Cricket Community App
Complete Feature & Architecture Documentation
Pre-Implementation Specification — Version 1.0
Platform: Flutter + Supabase
Region focus: Pakistan (grassroots / club / village cricket)
Introduction
This document is the complete pre-implementation specification for a community cricket application. It is the result of a detailed feature-by-feature design conversation, with every architectural decision documented, every edge case considered, and every open question resolved before a single line of code is written.
The app&apos;s purpose is to enable any user to create tournaments, manage club or village cricket teams, score matches (live ball-by-ball or post-match), track player and team statistics, and connect with the local cricket community. It is explicitly NOT tied to any single organization — every user has the ability to create and run their own cricket events.
How to read this document
Each feature is specified independently with its own Purpose, Phase tag (MVP / v1.1 / v1.2 / Phase 2), data entities, user flows, permissions, edge cases, and Supabase-specific implementation notes. Features 1–7 are individual specifications; Feature 8 is the architectural synthesis covering the complete data model, tech stack, and MVP scope freeze.

Core Principles (Locked Decisions)
The following principles were established before feature design began and govern every feature spec in this document. These are not suggestions — they are constraints that have been deliberately chosen and cannot be reopened without revisiting downstream specifications.
Player autonomy — Players are first-class users who can claim profiles, not just names attached to teams.
Flexible team membership — A player can be in multiple teams; tournament creators decide whether multi-team participation is allowed within their tournament.
Delegated scoring — The tournament creator owns scoring rights but can delegate to scorers, either at match-level or tournament-level.
Dual scoring modes — Live ball-by-ball OR post-match scorecard entry, chosen per match.
Derived stats — All rankings and statistics are auto-calculated from match data; nothing is entered manually.
Multi-format support — T10, T20, ODI, custom overs, tape-ball, hard-ball, and tennis-ball variants.
Hybrid claiming — Both invite-based and search-and-claim flows are supported, with stat transfer on claim.
Unclaimed players are tracked — Stats accumulate against unclaimed profiles; "verified" badge applies to claimed profiles.
Resilient scoring (post-MVP) — Mid-match mode switching, offline-first with sync (Phase 2), and co-scorers for redundancy.
Full format flexibility — Every cricket variable (overs, players, ball type, powerplay, max overs per bowler) is configurable per match or tournament.
All tournament structures supported — Knockout, round-robin, league (MVP), group + knockout (v1.1), double elimination (v1.2).
Location-aware — Geographic discovery, filtering, and profile location are core to the app.
No DLS — Rain-affected matches are handled simply (abandoned or rescheduled) or with custom rules per tournament.
Online-only ball-by-ball for MVP — Offline scoring deferred to Phase 2.
Phased delivery — Every feature is tagged with its phase; scope discipline is non-negotiable.
Owner / Manager separation — Teams have a single Owner (original creator, can transfer) and multiple Managers.
Feature 1: User & Authentication Model
Phase: MVP
1.1 Purpose
The User model is the foundation of the entire app. Every action — creating a tournament, scoring a match, claiming a player profile, posting content — is tied to a user. Authentication determines who they are; the user model determines what they can do and what data belongs to them.
1.2 User Types
There is one user type at the system level: a registered user. Roles like "tournament creator," "scorer," or "team captain" are contextual permissions, not user types. The same user can be a tournament creator in one tournament and a player in another.
Important: Do not create separate Player, Scorer, or Admin tables. One users collection, with roles assigned per context.

Create tournaments (becomes the creator/organizer of those)
Create teams (becomes the owner/manager of those)

Score matches unless explicitly assigned as a scorer

1.9 Edge Cases
Duplicate accounts: same person signs up with phone, then later with email → Phase 2 account merging tool.
Phone number recycled to a new owner → long-inactive accounts get phone unlinked after 12 months.
Username squatting (celebrity names) → report mechanism + admin review (Phase 2).
Account deletion vs deactivation → both options provided. Deletion is permanent and removes user data; deactivation hides profile but keeps stats.
Underage users: ToS requires 13+ minimum age.
Lost phone access → recovery via email backup (set during onboarding).

2.6 The Claim System (Hybrid)
Path A: Invite-based (manager initiates)
Team manager adds "Ahmed Khan" with phone number +92XXX.
System creates unclaimed_player record.
System checks if +92XXX is a registered user. If yes → in-app notification: "ABC Team added you as a player. Accept?". If no → SMS invite to download the app and claim.
When user joins/accepts, claimedByUserId is set and stats migrate.
Path B: Search-and-claim (player initiates)
New user signs up.
During onboarding, system suggests: "Search for your name in existing teams."
User searches "Ahmed Khan" → sees list of unclaimed profiles with team context ("Ahmed Khan in Lahore Lions, added by Bilal Ahmed").
User taps "Claim this profile."
Request goes to the team manager who added the player.
Manager approves or rejects — on approval, profile is claimed.
Edge cases for claiming
Same player in multiple teams as unclaimed → claiming one suggests claiming the others; each claim still requires separate manager approval.
Disputed claim (two users claim the same unclaimed profile) → first-come-first-approved by manager.
Rejected claim → user can still create a fresh profile but won&apos;t get the historical stats.
2.7 Multi-Team Membership
A player can belong to multiple teams. Per tournament, the tournament creator decides whether a player can be registered for multiple teams in that tournament. Globally, no restriction.
Example: Ahmed plays for "Lahore Lions" (club) and "Model Town XI" (village). Both are fine. But if both teams enter the "Spring Cup 2026" tournament and the tournament rule is "no multi-team," Ahmed must pick one for that tournament.

2.10 Edge Cases
Player added to team A, then claimed, then team A&apos;s manager wants to remove them — works normally; removal doesn&apos;t unclaim.
Owner deletes their account while owning a team — ownership transfers to first co-manager, or team is archived if none.
Two teams with identical names in the same city — allowed, but search shows location to disambiguate.
Banned/suspended user as a team member — remains in the roster (for stat continuity) but can&apos;t perform actions.
Player added to 50 teams (spam) — rate limit: max 10 active team memberships per player.
Team has 0 active players — flagged as Inactive but not auto-deleted.
Jersey number conflict — uniqueness enforced within a team only.

3.8 Fixture Generation — Per Format
3.8.1 Knockout
Teams are seeded (manually or randomly).
Bracket size rounds up to nearest power of 2 (8, 16, 32...).
Teams short of power of 2 get byes in round 1.
Round 1 winners advance to Round 2, and so on, until Final.
Optional 3rd-place playoff.
3.8.2 Round-Robin
Each team plays every other team once.
Total matches = n × (n-1) / 2.
Algorithm: Round-robin scheduling (circle method) — fairly distributes home/away and rest days.
Standings table maintained throughout.
3.8.3 League (Double Round-Robin)
Same as Round-Robin but each pairing plays twice (home + away).
Total matches = n × (n-1).
3.8.4 Group + Knockout (v1.1)
Teams split into groups (creator decides group count and size).
Each group plays a round-robin.
Top N from each group advance to knockout phase.
3.8.5 Double Elimination (v1.2)
Winners&apos; bracket and Losers&apos; bracket.
One loss → drop to losers&apos; bracket. Two losses → eliminated.
Final: Winners&apos; bracket champion vs Losers&apos; bracket champion.
3.8.6 Manual Override (all formats)
Manually edit fixtures (swap teams, change dates/venues).
Add/remove specific matches.
Reschedule matches.

3.10 Tournament Awards (Auto-suggested)
At tournament completion, the system auto-suggests awards. The creator confirms or overrides:
Best Batter — Most runs (tiebreak: average)
Best Bowler — Most wickets (tiebreak: economy)
Best All-rounder — Sum of runs + (wickets × 20), with min thresholds
Best Fielder — Most dismissals (catches + run-outs + stumpings)
Player of the Tournament — Highest impact score across all matches
Emerging Player (v1.1) — Best stats among players in their first tournament

3.13 Edge Cases
Team registers but withdraws before tournament starts — fixtures regenerated if not locked.
Tournament creator deletes account — ownership transfers to first co-organizer, or tournament locked/archived if none.
Two teams register the same player (multi-team allowed) — works; player&apos;s stats split across registrations.
Multi-team rule conflict — player tries to register with team B after team A in a no-multi-team tournament → blocked at registration.
Tournament has fewer than minTeams at deadline — creator notified; can extend deadline, reduce minTeams, or cancel.
Power-of-2 mismatch in knockout — handled via byes.
Fixture conflict (same team scheduled for two matches at same time) — system warns creator.
Cascading match impact in knockouts — system waits for completion before generating next round.

Feature 4: Match & Scorecard System
Phase: MVP (with phased complexity for scoring modes — see 4.2)
4.1 Purpose
A match is the atomic unit of cricket competition. Every score, stat, run, wicket, catch, and ranking ultimately traces back to a match. The match system must represent matches in any format, support both live ball-by-ball scoring and post-match scorecard entry, capture enough granular data to derive every stat in features 9–15 of the original wishlist, and handle interruptions (rain, abandonment, walkovers, ties, super overs).

Critical design decisions
Why store isFour / isSix as booleans even though they&apos;re derivable from runsScored? Because not all 4s/6s come from runs scored: a "4" via a no-ball (1 + boundary) is still a 4 for stats. Explicit fields prevent ambiguity.
Why legalBallNumber separate from ballNumber? Wides and no-balls don&apos;t count as legal deliveries, but they still need to be recorded as balls. Bowler stats (overs bowled) only count legal balls.
Why track both bowlerId and strikerId on every ball? For player stats. We need to attribute every run, wicket, catch back to specific players.
Why soft-delete (isDeleted)? Scorers make mistakes. Hard deletion corrupts history. Soft delete lets you "undo" a ball while preserving audit trail.

4.9 Scoring Modes
4.9.1 Live Ball-by-Ball Mode
The scorer is in the app during the match, recording every ball as it happens.
Display: Current bowler, striker, non-striker, score, overs.
Scorer taps outcome: 0/1/2/3/4/6/Wicket/Wide/NoBall/Bye/LegBye.
For wickets: secondary screen for wicket type, dismissed player, fielders involved.
For boundaries: confirm 4/6.
Ball recorded → next ball.
End of over: auto-rotate striker, prompt for new bowler.
Real-time sync: every ball insert pushes via Supabase Realtime to all viewers.
4.9.2 Post-Match Scorecard Mode
Match already happened; scorer is entering the summary after.
Enter team A innings: total runs, total overs, wickets.
Enter player batting cards: each batter&apos;s runs, balls, 4s, 6s, dismissal.
Enter bowling cards: each bowler&apos;s overs, runs, wickets, maidens.
Enter fielding contributions: catches, run-outs, stumpings.
Repeat for team B innings.
Mark match as completed.
Important: In scorecard mode, individual balls table entries are NOT created. Only aggregated player_innings_stats and innings totals are saved. Match still produces correct stats, but ball-by-ball replay isn&apos;t available.
4.9.3 Mid-Match Mode Switching (v1.1)
All ball-by-ball data captured so far is preserved.
A "scorecard supplement" is added for the remaining innings.
Stats engine handles both data sources for the match.

4.13 Edge Cases
Retired hurt batter returns — wicket fall logged as RetiredHurt; later innings continues with same player; their innings continues from previous score.
Mankad — recorded as RunOut with bowler as fielder.
Obstructing the field — its own wicket type.
Rain mid-over — scorer pauses; can resume from same ball or abandon.
Wide on last ball of innings — 7-ball over possible.
No-ball on last ball with boundary — 4 + 1 = 5 runs + ball must be re-bowled (with free hit).
Player retires out — counted as wicket.
Run out on a no-ball — ball is no-ball (1 extra) + dismissal.
Both batters run out on same ball — only one dismissal recorded; standard cricket rule.
Two new batters needed simultaneously — system prompts for new batter selection sequentially.
Scorer accidentally enters wrong batter as out — undo within 5 mins; otherwise creator override.
Network failure during live scoring — local queue + retry (Phase 2 offline).
Two scorers entering balls simultaneously — must use ball locking (only one scorer marked active at a time).
Match starts late, format reduced — creator can edit overs-per-innings before innings starts; not after.
Player listed in squad but didn&apos;t actually play — not selected in playing XI; doesn&apos;t appear in stats.

5.6 Why Materialized Stats Instead of Computed-On-Read
Answer: Performance.
Imagine "Top 100 batters in Pakistan." Computing on-the-fly would mean aggregating every legal ball faced by every player, summing runs and balls, and sorting — for thousands of users on every load. With materialized career stats, ranking queries become a simple SELECT ... ORDER BY totalRuns DESC LIMIT 100 — milliseconds.
Trade-off: Stats can be slightly stale (depends on trigger timing). For live matches, the player&apos;s current match stats are computed on-read; their career stats catch up after the match completes.
5.7 The Trigger Cascade
Data flow when a ball is recorded:
Ball inserted.
Trigger 1: Update innings totals.
Trigger 2: Update player_innings_stats for striker, non-striker (balls faced), bowler, fielders.
(Match completes...)
Trigger 3: Finalize player_innings_stats (notOut flags, etc.).
Trigger 4: Aggregate into player_career_stats.
Trigger 5: Update team_stats, tournament_stats.
Trigger 6: Update standings (if tournament match).
Trigger 7: Refresh ranking caches (async).
Each trigger is idempotent — running it twice produces the same result. Critical for handling retries and corrections.

5.9 Stat Migration on Profile Claim
Scenario: Ahmed Khan has been playing for 3 teams as an unclaimed player for 6 months. He&apos;s accumulated 450 runs and 22 wickets. Now he signs up and claims his profile.
User signs up → creates users row with userId = U1.
User claims unclaimed profile unclaimedId = X1.
Trigger fires:
All team_members rows where playerId = X1 → updated to playerId = U1, playerType = Claimed.
All player_innings_stats rows where playerId = X1 → updated to U1.
All balls rows where strikerId/nonStrikerId/bowlerId/fielderId/dismissedPlayerId = X1 → updated to U1.
player_career_stats row for X1 → renamed to U1 (or merged if U1 already had stats).
unclaimed_players.claimedByUserId = U1, claimedAt = now().
Ranking caches invalidated.
Edge case — Claiming multiple unclaimed profiles
Each claim is approved separately (per Feature 2).
After each approval, the same migration runs.
The user&apos;s career stats accumulate from each merge.
Edge case — Claim later disputed/reversed
Phase 2 — for now, claims are final once approved. Disputes go to admin (manual).

Hot path queries
Player profile load → career stats lookup
Tournament standings page → top performers
Global rankings → leaderboards
Match live page → current player stats
Caching strategy
Materialized views for ranking leaderboards (refreshed every 5 mins for active tournaments, hourly for global).
Redis cache (Phase 2) for hot leaderboard pages.
Real-time invalidation on match completion (trigger refreshes affected views).
Pagination
All ranking lists are paginated (default 25 per page). No "show all" option for global lists (could be 100,000+ players).
5.13 Data Integrity Rules
Stats must always be reconcilable from balls. Weekly reconciliation job (Phase 2) verifies this.
No negative stats — validated at the database level.
Strike rates / averages are computed, never stored as input. Stored only as cached values.
Unclaimed and claimed stats are first-class citizens. Both appear in rankings; unclaimed players are flagged but not excluded.
Stats from abandoned matches: runs/wickets up to abandonment count toward player stats; match counts as No Result for team standings.
Walkover matches: winning team gets a win in team stats; no player stats accumulated.
5.14 Edge Cases
Player claims profile mid-tournament — stats migrate live; rankings update on next refresh.
Two users claim the same unclaimed profile — first approved wins; second rejected with "Already claimed" message.
Manager removes a claimed player from their team — removal doesn&apos;t affect past stats; player remains in stats history.
Player banned post-stats accumulation — stats remain; profile hidden from rankings but data preserved.
Match corrected (ball edits days later) — stats recomputed via triggers; downstream rankings refresh.
Player&apos;s name changed — stats remain (linked by ID, not name).
Tournament cancelled mid-way — completed matches count for stats; cancelled matches don&apos;t.
Player on losing side hits century — century counts toward their stats; team loss counts toward their record. Both true.
Bowler&apos;s no-ball that gets a wicket — wicket NOT credited to bowler (it&apos;s a no-ball); runs counted to bowler.
Run-out attempt where batter survives — doesn&apos;t appear in stats at all (just a regular run).

Set visibility (Public default).
Post → appears in own feed + followers&apos; feeds.
Flow 2 — Following someone
Visit user/team/tournament profile.
Tap "Follow."
Confirm if private (v1.2).
Their posts now in your feed.
Flow 3 — Engagement
Like a post → tap heart → counter increments → author notified.
Comment on a post → tap comment → write → submit → author notified.
Reply to comment → opens reply thread → submit.
Flow 4 — Auto-milestone
Player scores 50.
End-of-innings trigger detects milestone.
Auto-post created, tagged with player + match + tournament.
Post appears in feeds of player&apos;s, team&apos;s, tournament&apos;s followers.
Player gets a "You hit a milestone!" notification.
6.16 Edge Cases
User posts then deletes account — posts are anonymized ("Deleted user") or hard-deleted based on user choice.
Tagged player wants to be untagged — tagged users can remove their tag from any post.
Post about completed match, then match is corrected — auto-posts auto-update; user posts don&apos;t.
Mass-follow spam — rate limit: max 50 new follows/hour.
Deleted user&apos;s posts in feeds — show as "[deleted]" or filter out.
Inappropriate auto-post (e.g., milestone post for a player who lost) — opt-out per category in Settings.
Post on private team/tournament — only visible to members.
Mention a non-existent username — text remains as-is, no link, no notification.
Block someone who&apos;s a teammate — works; they remain teammates. Block only affects social interactions.
Auto-post for unclaimed player — created but addressed to the unclaimed entity. When claimed later, the post appears in their feed history.

8.4.2 Architectural Pattern
Clean-ish architecture, pragmatic edition:
presentation — Widgets only. No business logic.
application — Riverpod providers. Coordinates between presentation and data.
data — Repositories. The only layer that talks to Supabase.
This separation matters because if Supabase ever needs replacing later, only data/ changes.
8.4.3 State Management Strategy
Riverpod providers for everything reactive
AsyncValue for loading/error states
StateNotifier / Notifier for complex stateful logic (live scoring controller)
Stream providers for Supabase Realtime subscriptions
Example: Live match scoring uses a MatchScoringNotifier that subscribes to balls table via Realtime, maintains local optimistic state for fast UI, reconciles with server confirmations, and exposes a clean API: scoreBall(BallInput), undoLastBall(), etc.

Appendix B: Glossary
Term
Meaning
Claim
When a real user takes ownership of an unclaimed player profile created by a team manager
Co-scorer
An additional scorer assigned to a match for redundancy (v1.1)
DLS
Duckworth-Lewis-Stern — proprietary rain-rule algorithm; explicitly NOT used in this app
Innings (singular and plural)
A team&apos;s batting period in a match. A T20 match has 2 innings (one per team)
Legal ball
A delivery that counts toward the over&apos;s 6 balls (excludes wides and no-balls)
MOM
Man (or Player) of the Match — best individual performance in a match
NRR
Net Run Rate — tie-breaker metric: (runs scored / overs faced) − (runs conceded / overs bowled)
Powerplay
Initial overs of an innings with field restrictions
Round-robin
Tournament format where every team plays every other team once
Squad
List of players a team registers for a specific tournament (subset of full roster)
Super Over
One-over-per-side tiebreaker for tied matches
Tape-ball cricket
Pakistan&apos;s hugely popular informal format using a tennis ball wrapped in electrical tape
Unclaimed player
A player profile created by a team manager for someone not yet on the app
Walkover
Match awarded to one team because the other failed to show up
